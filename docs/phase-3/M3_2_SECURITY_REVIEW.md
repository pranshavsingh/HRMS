# HRMS SaaS — Milestone M3.2 Security Review
## Cryptographic Architecture, Data Protection at Rest, Key Management & Threat Modeling

**Scope:** Distributed Queue, Outbox Table, Cryptography Utility, OTP Processing  
**Security Standard:** OWASP ASVS Level 2, NIST SP 800-38D (GCM mode), Phase 1 Security Baseline Compliance

---

## 1. Cryptographic Design & Payload Protection

In the Phase 3 distributed architecture, background jobs are serialized into MySQL `outbox_events` and enqueued into Redis BullMQ streams. If plaintext arguments were stored directly in database records or Redis hashes, database backups, replication replicas, and cache inspection tools would expose sensitive user credentials (such as temporary OTP tokens and PII).

### 1.1 AES-256-GCM Envelope Encryption
All sensitive outbox payloads are encrypted at the moment of creation using **AES-256-GCM** (Galois/Counter Mode), providing both confidentiality and cryptographic integrity verification:
- **Algorithm:** `aes-256-gcm`
- **Key Length:** 256 bits (32 bytes), validated on startup.
- **Initialization Vector (IV):** 12 bytes generated cryptographically per payload using `crypto.randomBytes(12)`. IV reuse is mathematically impossible across events.
- **Authentication Tag:** 16 bytes generated by GCM mode (`cipher.getAuthTag()`).
- **Encrypted Envelope Structure:**
  ```json
  {
    "version": 1,
    "iv": "e3b0c44298fc1c149afbf4c8",
    "authTag": "9f86d081884c7d659a2feaa0c55ad015",
    "ciphertext": "a1b2c3d4..."
  }
  ```

### 1.2 Tamper Resistance & Authenticated Decryption
During worker execution:
- The handler unpacks the envelope and invokes `decryptPayload(envelope)`.
- Node.js crypto sets the auth tag (`decipher.setAuthTag(tagBuffer)`).
- If any byte of the ciphertext, IV, or authentication tag has been tampered with or corrupted in transit, the decipher throws an immediate authentication failure error (`Unsupported state or unable to authenticate data`).
- The worker quarantines the record without attempting to execute malformed instructions.

## 2. Key Management & Operational Security

### 2.1 Encryption Key Isolation
- The encryption key is sourced exclusively from the environment variable `OUTBOX_ENCRYPTION_KEY`.
- **Validation on Boot:** `env.js` validates that `OUTBOX_ENCRYPTION_KEY` is present and at least 32 characters long. In production (`NODE_ENV === 'production'`), weak placeholders (such as `change-this-in-production`) trigger an immediate fatal startup error (`process.exit(1)`).
- **Environment Isolation:** The encryption key is required only on API servers (to encrypt outbox records) and dedicated Worker servers (to decrypt and process jobs). It is never shared with the frontend, mobile app, or client-facing responses.

### 2.2 Redis Connection URL Sanitization
- Redis URLs often contain inline passwords (e.g. `redis://:secret_password@10.0.0.1:6379/0`).
- `src/config/queue.js` contains a dedicated `sanitizeRedisUrl()` helper that masks passwords before outputting any connection string to Winston logs or error traces:
  ```
  redis://:******@10.0.0.1:6379/0
  ```

## 3. Threat Modeling & Attack Surface Evaluation

| Threat Vector | Mitigation Strategy | Verification Status |
| :--- | :--- | :---: |
| **Database Read Compromise (SQL Injection / Data Leak)** | An attacker obtaining read-only access to `outbox_events` sees only AES-256-GCM ciphertext. Without `OUTBOX_ENCRYPTION_KEY`, the attacker cannot extract OTPs or reset user passwords. | **VERIFIED** |
| **Dual-Write Inconsistency** | Outbox event is committed inside `db.transaction()` along with the business state. If the transaction aborts, neither the OTP nor the outbox event exists. | **VERIFIED** |
| **Worker Double-Execution / Replay** | Outbox events are assigned deterministic BullMQ Job IDs (`outbox_<id>`). Redis rejects duplicate enqueues. Handlers check DB state (`is_consumed`) before dispatch. | **VERIFIED** |
| **Poison Pill Denial of Service** | Malformed payloads are trapped in a localized `try/catch` and quarantined to `DEAD_LETTER`. Worker threads never crash or enter infinite retry loops. | **VERIFIED** |
| **User Enumeration on Password Reset** | `POST /accounts/auth/password-reset-otp` returns identical generic messages and response timings whether the user exists or not. | **VERIFIED** |
| **Plaintext Credential Logging** | Winston deep redaction masks `otp`, `password`, `token`, `authorization`, and `ciphertext` in all logging pipelines. | **VERIFIED** |

## 4. Preservation of Phase 1 Security Controls

All Phase 1 security controls remain fully intact and active:
1. **Password Policy**: Minimum 12 characters, maximum 128 characters, Bcrypt with 12 rounds.
2. **JWT Security**: Strictly rejected query parameters (`?token=`), rejection of `'none'` algorithm, refresh token rotation with session family revocation.
3. **RBAC & IDOR**: Role checks enforced in middleware, employee cross-tenant access blocked.
4. **Media Protection**: Static `/media/documents` blocked from direct unauthenticated access.
5. **CORS Hardening**: Strict origin allowlist, wildcard origin blocked in production.
